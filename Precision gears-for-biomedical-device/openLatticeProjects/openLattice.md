BoneScaffoldAI: OpenSCAD review for medical and architectural applications

Your code is a promising parametric geometry generator for porous structures. Its strongest feature is the ability to create a cylindrical specimen with configurable dimensions, intersecting struts, optional end plates, and an optional axial hole—or import a porous STL generated by an external tool.

The same underlying approach can be useful in two very different fields:

    Medical engineering: exploratory bone-scaffold geometries, porous biomaterial research, and mechanical test specimens.

    Architecture and construction: lattice panels, lightweight structural cores, modular infill, and cellular design studies.

However, the two applications impose different requirements. Medical scaffolds need particular attention to pore architecture, biological compatibility, and implant-specific validation. Architectural structures need attention to load paths, buckling, connections, manufacturability, and building-code requirements.

My central recommendation is to retain the current code as a geometry prototype and develop separate, application-specific design and validation workflows around it.

Your built-in model combines three families of struts:

    Vertical struts running along the Z-axis.

    Horizontal struts running along the X-axis.

    Horizontal struts running along the Y-axis.

These are clipped to a cylindrical envelope using intersection(). The optional plates and center hole modify the resulting geometry.

With the supplied defaults, the nominal specimen is 12 mm in diameter and 20 mm tall, with a 4 mm grid spacing and 1.1 mm nominal strut diameter.

This produces a regular, orthogonal lattice—not a model of actual trabecular bone, a clinically optimized scaffold, or an engineered structural lattice validated for building loads.

That distinction matters when deciding what applications the code can support today.

Medical-specific code review
Issue M1 — The default pore scale is probably too coarse for many bone-scaffold studies

Your defaults are:
cell_size = 4;
strut_radius = 0.55;

The nominal spacing between adjacent parallel struts is 4 mm, and their nominal clear gap is approximately 2.9 mm, or 2,900 µm.

That is much larger than the pore dimensions often investigated in bone tissue engineering. Published reviews discuss a broad range of scaffold pore sizes, including ranges of a few hundred micrometres, while emphasizing that there is no universally optimal pore size. 
Frontiers
+1

This does not make your model wrong. It means the default settings are better suited to a coarse demonstrator unless a specific experimental objective justifies that pore scale.

Recommended improvement: Separate the design parameters from the intended biological targets.
// Geometric parameters, in mm
cell_size = 0.8;
strut_radius = 0.10;

These values are only an example of a finer geometric study, not a validated medical prescription. They may require different manufacturing equipment, and smaller features can become difficult to print accurately.

More importantly, cell_size is not itself the pore diameter. The actual pore size must be measured from the generated geometry.
Issue M2 — The lattice is not anatomically or mechanically adaptive

All three strut families use the same radius and a regular grid. The result is uniform and predictable, but does not adapt to local anatomical shape, loading, or desired biological behavior.

Recommended improvement: Introduce a spatially varying design, for example:

    Different strut radii in different regions.

    Gradually changing cell spacing.

    A denser peripheral shell with a more porous interior.

    A solid-to-porous transition region.

    A geometry generated from a patient-specific anatomical surface.

OpenSCAD can be part of such a workflow, but advanced grading and anatomical adaptation may be easier to compute in a dedicated mesh-processing or computational-design pipeline, with OpenSCAD handling final geometry assembly.
Issue M3 — There is no quantitative porosity or pore-connectivity analysis

The code generates a shape, but it does not calculate:

    Porosity as a percentage of total volume.

    Pore-size distribution.

    Minimum strut thickness.

    Interconnected pore pathways.

    Surface area or permeability.

These are not cosmetic metrics. Reviews of scaffold architecture note that pore volume and mean pore size alone do not fully describe transport behavior; permeability and connectivity are also important.

+1

Recommended improvement: Add a downstream analysis stage that measures the exported mesh and, where appropriate, simulates fluid flow. Treat these as separate validation outputs rather than inferring them from cell_size.
Issue M4 — The geometry generator does not establish medical suitability

The warning at the top of your code is appropriate. Keep it.

For any implant-directed work, the workflow would additionally need material characterization, biocompatibility assessment, sterilization considerations, mechanical and fatigue testing, manufacturing validation, and a regulatory strategy appropriate to the intended use.

Medical verdict: Good for generating experimental geometry and comparative prototypes. Not sufficient, on its own, for designing or validating a patient implant.

C. Acoustic, shading, and decorative elements

Porous geometries could be used as the basis for shading screens, decorative partitions, or experimental acoustic panels.

These applications would need additional geometry controls for light transmission, airflow, cleanability, sound absorption, and the intended installation method. The current code does not predict those properties.
Architecture-specific code review
Issue A1 — The model is limited to a cylindrical specimen

The current envelope is:
module specimen_boundary() {
    cylinder(
        h = scaffold_height,
        d = scaffold_diameter,
        center = false
    );
}

This is useful for test cylinders, but architectural components often need rectangular panels, beams, shells, curved façades, or components fitted to existing geometry.

Recommended improvement: Decouple the lattice generator from the specimen boundary. Conceptually, use a configurable boundary module that can represent a cylinder, box, or imported envelope.

For example, a rectangular envelope could be implemented as:
module rectangular_boundary(
    width,
    depth,
    height
) {
    cube([width, depth, height], center = false);
}

For this box, the lattice coordinates would also need to be changed to use the box's coordinate system. Simply swapping the boundary module without adapting the strut placement would not produce a centered or fully filled panel.
Issue A2 — Uniform cells are not optimized for load paths

Your code distributes struts uniformly. Architectural components, however, may experience bending, torsion, compression, or mixed loading.

Recommended improvement: Introduce load-informed design parameters rather than assuming uniformity is optimal. A future implementation could vary strut thickness or topology according to results from finite-element analysis.

For a structural component, validation should include appropriate material properties, boundary conditions, load combinations, buckling, connection details, fatigue where relevant, and physical testing. Research on architected lattice materials highlights instability and post-buckling as important failure mechanisms.

Issue A3 — End plates are not yet a complete architectural connection system

The optional plates are useful as geometric end caps, but they do not define fasteners, bolts, bearing surfaces, joining details, or tolerances.

Also, in the original code, plate_extra_radius is clipped away by the outer cylindrical intersection. The earlier proposed Boolean restructuring corrects this if an overhanging plate is intended.

For architectural use, I'd add explicit connection modules, minimum wall and ligament thicknesses, and manufacturing clearances. For load-bearing parts, these dimensions must be derived from engineering requirements rather than visual preference.

Architectural verdict: The code is a useful basis for porous infill, façade concepts, and cellular design studies. It is not yet a structural-design or building-compliance tool.

A particularly important improvement: make the nodes intentional

The hull() operation creates capsule-like struts with rounded ends. When the struts intersect, the overlapping spheres and capsules produce enlarged junction regions.

This is computationally convenient, but the junctions are not explicitly designed. Their geometry can influence stress concentrations, local material volume, printability, and the shape of the pores.

For medical research, you may want controlled transitions between struts and a measurable pore network. For architecture, you may want designed node geometry and predictable load transfer.

I would make node geometry a separate design concern rather than relying exclusively on overlapping rounded struts.
